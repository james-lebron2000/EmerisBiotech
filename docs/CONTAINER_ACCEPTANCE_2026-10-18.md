## Execution gates and planned checks

The build context is reconstructed from source files plus `pyproject.toml` and `uv.lock`. Unexpected source file types, linked source files, oversized files, raw evidence, SQLite databases, exports, examples and output folders cannot enter the context. Actual copied bytes must match the snapshot. An exact snapshot of the repository Dockerfile is used as a separate build control file, with its SHA recorded. Build uses cached dependencies, prechecks every base image is local, sets `--pull=false`, `--network none` and a 240-second bound; cache misses requiring dependency downloads fail explicitly. Container runs use `--pull=never`. Only the explicitly bounded official Caddy pull may retrieve an image. The image's entire packaged source manifest must match the frozen snapshot.

Fresh randomly named QA volumes, containers and networks are the only runtime resources used. The app has no host-published port and connects only to an internal backend, whose engine `Internal` property is checked. The worker runs with `--network none`; engine configuration and loopback-only interfaces are both checked. Both use UID/GID 10001, a read-only root filesystem, dropped capabilities, bounded tmpfs, memory and PID limits. Volumes contain synthetic fixtures only. The worker's fully disconnected QA topology is intentionally stricter than Compose's separate collection-egress network; it does not prove actual registry connectivity.

Worker checks use the real standalone worker process and actual Docker SIGTERM/exit/restart. They exercise recovery of an explicitly seeded dead-owner queue item and execution of a configured offline intake with missing original evidence; scheduler collection remains disabled and no public data fetch is permitted. This does not simulate killing a real in-flight external clinical-data request.

The optional HTTPS stage uses the exact repository Caddyfile through a temporary wrapper, with a disposable QA certificate and generated QA credentials. Client requests explicitly trust only the temporary QA CA; a separate client without that CA must reject it. System trust is never changed, and TLS verification is never disabled. Planned checks are unauthenticated/incorrect-credential 401, authenticated 200, protected attachments, rejected Origin/CSRF, a valid authenticated synthetic note and persistence after app restart. See the official [Caddy authentication](https://caddyserver.com/docs/caddyfile/directives/basic_auth) and [certificate directives](https://caddyserver.com/docs/caddyfile/directives/tls).

The final JSON report must record source commit and dirty status, source/tree hashes, dependency and deployment-control hashes, built image ID, actual checks/errors, exact dedicated resource names, retained image, cleanup results and before/after unrelated-container inventory. Container names are recorded before mutation; cleanup verifies each run's ownership labels and continues after individual failures. Already removed ephemeral containers are recorded separately. A real final check compares the unrelated running-container ID/name inventories irrespective of list order; an inventory command error or difference fails acceptance. Any unremoved resource, changed frozen input or final disk-budget violation also makes the result failed. These failures retain the cleanup report. Generated private keys and authentication configuration are deleted after the run. QA images are retained; no image or production resource is deleted. An explicit `--skip-gateway` produces only a partial result, never a full acceptance pass.
