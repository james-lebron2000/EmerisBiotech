# 产品总目标与完成判据

用户目标：迭代完善 Virtual Biotech，制作一个能够塑造顶级 AI Native biotech 的产品；独立提出 Issue、设计方案解决并更新到 GitHub。

AI Native 需要把证据、研究建议、任务、真实工具回执和后续决定连接起来，并验证这种工作方式的价值。当前已接入会话生成草案及两项主机定义只读工具，尚不具备产品内自主模型调用、完整任务编排或经前瞻验证的研发优势。工程问题以 GitHub Issue 与可审阅 PR 跟踪，不以发布代码替代科学及用户价值验收。

本目标持续有效。2026-10-26 开始将已有证据研究、临床资产与记录基础扩展为研发项目决策系统。此前以临床预测与投资为核心的文档保留为历史方向及可继续验证的工作流；不能用投资看板或单一 UC 案例代替本次完整目标。

## 产品必须服务的工作

产品帮助团队从患者未满足需求形成可证伪项目，持续检验靶点、药物形式、差异化和商业可行性，安排下一项最关键验证，在明确成本和风险的情况下配置项目组合资源，并保留停止和失败记录。2026-10-26 用户明确选择“研发团队和投资/BD 两者都需要，先用一个 UC 项目贯通”。两类角色共用来源、分析与版本，分别记录研发决定和资产尽调，不把研究关联直接转成成功概率、权利或收益判断。

“顶级 biotech”是对最终用途的要求，不能通过增加功能、模型数量、代理数量或测试数量单独验收。需要实际研究者使用产品作出更好决策，并有独立、前瞻、同等资源比较的证据。药物资产、临床效果、融资及交易结果均不因软件发布而成立。

## 当前切入与迭代顺序

首个切入使用 UC 项目，因为已有独立重算与反证，可实测产品是否阻止了不当外推。首轮增加研发项目、证据范围、版本修订、拟议验证计划和决定记录。所有导入证据保持待审阅，无伪造负责人、预算或人工决定。

当前已补“验证结果回写—计划标准比对—下一次决定”的软件闭环，并在同一 UC 项目关联外部临床参考资产、增加独立的 BD 尽调记录。下一轮增加项目风险分解与证据覆盖，逐步接入实际研究执行和有资源约束的组合比较。每轮保留范围、运行与验收记录；在来源与人员未落实时显示缺口。

预测、BD 或投资工作流只有在明确业务范围、来源使用权、时点和独立评价后进入相应验收，不能以事后已知结果构造前瞻成功记录。
